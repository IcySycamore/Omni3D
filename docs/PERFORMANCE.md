# 重建速度与质量（实测）

> 复现：`.\run.ps1 bench`（全部示例）或
> `.\run.ps1 bench --frames 4 8 12 --res 224 512 --repeat 3`
>
> 脚本：`scripts/bench_reconstruct.py`

## 测量环境

| 项   | 值                                                              |
| ---- | --------------------------------------------------------------- |
| GPU  | 本机 CUDA（`torch.cuda.is_available() == True`）                |
| 模型 | Fast3R ViT-Large（`jedyang97/Fast3R_ViT_Large_512`）            |
| 数据 | `demo_examples/` 5 个示例视频，`cv2` 均匀抽帧                   |
| 口径 | 每次 warmup 1 次后计 1 次；耗时含抽帧后**加载→推理→对齐**全流程 |
| 版本 | torch 2.5.1+cu121                                               |

## 速度

**结论：`512px` 约 0.17 s/帧，`224px` 约 0.05 s/帧（约 3.4× 差距）。**

按分辨率的中位数（n=15）：

| 分辨率 | 每帧耗时（中位） | 12 帧端到端 |
| ------ | ---------------: | ----------: |
| 224    |    **0.05 s/帧** | 0.5 ~ 0.9 s |
| 512    |    **0.17 s/帧** | 2.0 ~ 3.5 s |

### PLY 数值精度：坐标升为 `double`（#24）

坐标由 `<f4` 改为 `<f8`（header `property double x/y/z`），同时
`apply_similarity` 不再把 float64 结果回写成 float32 —— 整条导出链路不再经过 float32。
颜色仍是 `uchar`（3B/点）。

| 项                                                  | float32（旧） |                float64（现） | 变化 |
| --------------------------------------------------- | ------------: | ---------------------------: | ---: |
| 字节/点                                             |            15 |                       **27** | ×1.8 |
| PLY 体积（2,027,138 点，family 16 帧 @512，SOR 后） |     ≈ 30.4 MB | **54,732,164 B（52.2 MiB）** | ×1.8 |
| PLY 体积（1,460,540 点，family 12 帧 @512）         |       20.9 MB |   ≈ 37.6 MB（按 27B/点推算） | ×1.8 |

**必须说清楚：这不是一次精度提升。** float32 的相对精度约 `1.2e-7`
（1m 处 ≈ 0.12µm），而实测自洽性误差约 2.5%（1m 处 ≈ 2.5cm），
两者差 5 个数量级 —— float32 从来不是误差瓶颈。这项改动只是
「既然不要速度，就顺手把无谓的二次舍入去掉」，代价是 PLY 体积 ×1.8。

渲染子集**仍刻意保持 float32**：屏幕分辨率远低于 float32 精度，用 double 白占内存。

复现：`python scripts/sor_report.py` 会一并打印 PLY 体积与「字节/点」。

### 全量点云吸附（#25）

客户端拿到的 `points` 是**渲染子集**（默认 6 万 / 全量约 200 万），等于每约 24 个点
只留 1 个、点距被放大约 5 倍。所以选点后要拿坐标回来吸附到**全量点云**上，
测量才不带上采样误差。实现见 `web/snap_index.py`（`cKDTree` + 按会话 LRU）。

实测（family 16 帧 @512，SOR 后 2,026,141 点）：

| 项                  |                      值 |
| ------------------- | ----------------------: |
| 读 PLY（52.2 MiB）  |                  0.06 s |
| 首次请求（含建树）  |              **0.54 s** |
| 批量查询 200 点     | **16.8 ms（84 µs/点）** |
| 命中                |               200 / 200 |
| 坐标内存（float64） |                46.4 MiB |
| 缓存                | 首次 miss、第二次起 hit |

结论与注意：

- 单次点选（1~4 点）延迟约 0.5s **只在会话首次**；之后每次请求是毫秒级。
  所以界面上「第一次选点略顿、之后跟手」是预期行为。
- ⚠️ **内存比原估的大**：issue 里按「3 个会话 ≈ 52MB」估的，实测单会话坐标就
  46.4 MiB，`cKDTree` 内部另存一份，**单会话实际约 90~100MB**，3 个约 270~300MB。
  容量可用 `OMNI3D_SNAP_CACHE` 调小（默认 3）。
- 84 µs/点比 issue 里估的 10µs 高，因为这里含线程池首次调度；批量提交仍是
  **一次** RPC，所以看不出差别。
- 缓存以「文件大小 + mtime」为签名：PLY 被覆盖会自动重建树，不会吸附到旧点云。
  删除会话时会主动失效。

## 质量（**代理指标**，非绝对精度）

⚠️ 本机**没有 GT 点云/位姿数据集**，因此下面衡量的是**自洽性与稳定性**，
不能等同于绝对精度。绝对精度需跑 vendored 的 `fast3r/eval/`
（依赖 re10k / robustmvd 数据集，本机未附）。

| 指标              | 含义                                                       | 理想                                 |
| ----------------- | ---------------------------------------------------------- | ------------------------------------ |
| `residual_ratio`  | local head 与 global head 对齐后的残差 RMS ÷ 点的 RMS 半径 | 越小越自洽                           |
| `local_scale_std` | 各视图 local→global 拟合缩放的离散度                       | 越小越一致                           |
| `mean_conf`       | **所选 head** 的平均置信度（随 `source` 走）               | 仅作参考，两档量纲不同，**不可互比** |

观测（30 组）：

- `residual_ratio` 中位 **0.0251**，范围 **0.0100 ~ 0.0981**
- 最好：`kitchen`（残差 0.010、尺度离散 0.0012、置信度 17.3）
- 最差：`family`（4 帧 224 时残差 0.096）、`lighthouse`（尺度离散 0.066~0.078 最高）
- 分辨率提升会明显改善自洽性：例如 `family` 4 帧 224→512，残差 0.096→0.044；
  12 帧 512 时残差降到 0.028

### 点云来源：local head vs global head（#21）

`OMNI3D_PTS3D_SOURCE` 环境变量（或 `run_reconstruction(..., pts3d_source=...)`）
可选两档，默认 `local`：

- `local`（**默认**）→ `pts3d_local_aligned_to_global` + `conf_local` ——
  local head 经 `align_local_pts3d_to_global` 对齐到全局坐标系；
  与上游重建评测口径一致（`configs/model/fast3r.yaml` 的
  `eval_use_pts3d_from_local_head: true`）。
- `global` → `pts3d_in_other_view` + `conf`（全局 head 原始输出）。

两者都在**同一全局坐标系**，下游（米制尺度变换 / 置信度过滤 / PLY / 渲染）
无需区分；且**一次前向同时产出两种输出**，因此切换**零成本**（无需重跑模型）。

实测（`family` 16 帧 @512，单次前向 4.3 s，16 视图）：

复现：`python scripts/ab_pts3d_source.py`。总点数存在 <0.1% 的跑次间波动
（cuDNN 非确定性 + 位姿估计），几何一致性结论稳定。

| 项                                       | `local`（默认）             | `global`                    |
| ---------------------------------------- | --------------------------- | --------------------------- |
| 过滤前总点数                             | 2,359,296                   | 2,359,296                   |
| 过滤后总点数（`VIS_CONF_PERCENTILE=10`） | 2,123,463                   | 2,123,908                   |
| 单视图点数（min/中位/max）               | 132,710 / 132,715 / 132,726 | 132,712 / 132,718 / 133,089 |
| 过滤后均值置信度                         | 18.78                       | 13.99                       |
| `residual_ratio` 中位                    | **0.027043**                | **0.027043**                |
| `local_scale` mean ± std                 | 0.485676 ± 0.034830         | 0.485676 ± 0.034830         |

结论：

1. `residual_ratio` 与 `local_scale*` **两档完全相同** —— 它们在对齐阶段算出，
   与「取哪个 head 出点云」无关，因此**不能**用它们区分两档优劣。
2. 两 head 的点云几何差异极小：中位最近邻距离 **0.00249**，仅占场景对角线
   （7.86）的 **0.032 %**（对称 Chamfer 中位同为 0.032 %）。即本机场景下两档
   几乎给出同一份重建，切到 `local` 主要是**与上游评测口径对齐**，
   而非一次肉眼可见的精度提升。
3. `mean_conf` 两档为 18.78 / 13.99，**量纲不同、不可互比**，
   只能在同一档内做纵向/横向对比。

### 离群点剔除（SOR，#22）

面积误差 ~ 平方级、体积误差 ~ 立方级放大，几何飞点必须先剔除。它与置信度过滤
**互补**：置信度删的是「模型没把握的点」，而背景飞点往往置信度并不低，只能靠
**几何孤立性**（k 近邻平均距离显著偏大）识别。

开关：`OMNI3D_SOR_K`（默认 8）/ `OMNI3D_SOR_STD`（默认 2.0），**任一为 `0` 即关闭**。
剔除后的点云**同时**用于显示、PLY 导出与测量（看到的 = 量到的 = 导出的）。

实测（family 16 帧 @512，同一份点云；前向 3.85 s 作参照）：

| 项                     | 值                                             |
| ---------------------- | ---------------------------------------------- |
| 置信度过滤后（SOR 前） | 2,123,457                                      |
| SOR 后（k=8, std=2.0） | 2,027,138                                      |
| 剔除                   | **96,319（4.536 %）**                          |
| 纯算法耗时             | **1.02 s**（0.48 µs/点，约等于前向耗时的 26%） |
| 剔除后抽样渲染         | 60,000（仍能填满上限）                         |

参数敏感性（同一份点云）：

|   k | std | 剔除比例 % | 耗时 s |
| --: | --: | ---------: | -----: |
|   8 | 1.0 |     11.857 |   0.93 |
|   8 | 2.0 |      4.536 |   0.93 |
|   8 | 3.0 |      1.923 |   0.92 |
|  16 | 2.0 |      4.512 |   1.21 |
|   4 | 2.0 |      4.541 |   0.85 |

结论：

- **`std` 决定剔除强度**，`k` 几乎不影响比例（4/8/16 都在 4.5 % 上下）——
  调「剔多少」应该动 `std`，而不是 `k`。
- 代价可控：全量建 cKDTree + 查 k 近邻约 1 s，远小于推理本身；
  分块查询把峰值内存从 ~300MB 压到 ~70MB。
- ⚠️ 这里只验证了「剔掉多少」，**尚未验证「剔得对不对」**（没有 GT）。
  绝对精度校验属 #26（`scripts/measure_error.py` + 自建 GT 数据集）。

复现：`python scripts/sor_report.py`（可选参数：视频路径、帧数、分辨率）。

## 实践建议

| 场景                            | 建议                                                      |
| ------------------------------- | --------------------------------------------------------- |
| 快速预览 / 迭代（同效果看一眼） | `224`，4~8 帧（≈0.2~0.6 s）                               |
| 正式出点云                      | `512`，10~16 帧（≈2~3.5 s，点数 1.5M~2.4M）               |
| 纯网页无 AR 位姿                | 任意尺度，需「标尺校准」                                  |
| 有 AR 位姿                      | 服务器自动对齐到米制（见 `docs/ARCHITECTURE.md` 第 6 节） |

> 速度瓶颈在 ViT 编码，与帧数近似线性；分辨率影响约平方级（512 是 224 的 ~3.4 倍时长）。
