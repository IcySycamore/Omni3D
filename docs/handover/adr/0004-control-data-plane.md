# ADR-0004：控制面 / 数据面分层与账务归属

- 状态：Accepted
- 日期：2026-09-17
- 关联：ADR-0002、ADR-0005、[`../02-wire-protocol.md`](../02-wire-protocol.md)

## 背景

参考实现里，Portal（官网）与 Api（服务商）**共享同一个 SQLite 文件**、共享同一份认证实现，
靠"同机"成立。一旦两个服务独立部署，这条路就断了；而 Api 在热路径上（每次提交任务）都必须知道
"这把 Key 有效吗、这个账号有没有额度"。

## 决策

**控制面数据只归 Portal；数据面数据只归 Api。**

| 归属                 | 数据                                                           | 存储                                                                        |
| -------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **Portal（控制面）** | 账号、计划包、用量包、余额、订单、流水、API Key（只存 sha256） | **Portal 独占的 Postgres 数据库**                                           |
| **Api（数据面）**    | 任务、会话、标注/测量、产物元数据、用量**原始记录**            | **Api 自己的 Postgres**（同实例不同 schema/角色即可）+ **S3/MinIO**（产物） |
| **共享**             | 认证协议（挑战-应答）与 DTO 契约                               | `Omni3D.Shared` 类库（**不是**共享数据库）                                  |

- **Api 不直连控制面数据库**：校验 Key 与上报用量都走 **Portal 的内部 API**（gRPC 或 REST），
  传输用 **mTLS**（双向证书，只在内网/同机网段开放）；
- 账务表（accounts/packs/orders/ledger）**只有 Portal 能写**；Api 只能"请求扣减"与"追加用量事实"；
- 用量以 `task_id` 为幂等键上报，因此"重复上报"不会重复扣费；
- 吊销即时生效（因为每个请求都过 Portal）——这是分层白送的好处。

## 代价与后果

- **热路径多一跳**：提交时校验 Key 要同步调 Portal（内网 RTT 可忽略；Portal 挂 → 明确 503，
  见 ADR-0005 的失败策略）；
- **两套数据库/迁移**：运维复杂度上升（换来的是"分机器部署"与"账务不可从数据面篡改"）；
- **几何迁移是真的工作量**：吸附（cKDTree）、SOR、测量、PLY 读写全部要重写为 .NET 实现，
  且必须与冻结基线数值一致（用参考实现的测试向量做回归）；
- **不能靠共享文件"抄近路"**：任何"两个服务读同一个 SQLite"的实现都是对本次决策的违反。

## 未决

- 内部 API 的形态：gRPC（推荐，与 worker 一套工具链）或 REST + mTLS；
- 是否给 Api 加"短 TTL Key 缓存"以降 RTT（**默认不做**：会牺牲吊销即时性）；
- 数据面是否允许"单机 SQLite 模式"作为开发/极小客户配置（建议允许，仅限 `Development`）。
