# 行业调研（拆成 panel 侧 / 服务侧）

> 为什么拆：**panel 是"3D 编辑器"，服务是"重建服务商"，两者该抄的对象完全不同**
> —— 把 WebODM 当 panel 的参照会跑偏（它是项目管理面板，不是编辑器）。
> 逐项能力对比表（30+ 项）见 [`../RELATED-WORK.md`](../RELATED-WORK.md)。

---

## 一、panel 侧（我们要先做的这一半）

### 1.1 参照对象

| 对象                                 | 是什么                                                                               | 能从它身上拿到什么                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| **Potree**                           | 大点云 web 查看器 + 示例应用（八叉树 LOD、点/高/面积/体积测量、annotation、profile） | **LOD 流式的成熟做法**（八叉树 + 按视锥/屏幕误差取块）、测量工具的交互范式     |
| **CesiumJS**                         | 地理空间 3D 引擎                                                                     | **3D Tiles 消费端**（点云/瓦片调度）、相机与尺度（米制）处理、LOD 调度器       |
| **SuperSplat / PlayCanvas**          | 高斯泼溅编辑器（看/裁剪/删飞点/发布）                                                | **编辑器 UX**：框选、变换、发布链接、撤销栈的粒度；以及**单文件发布**的思路    |
| **three.js editor / Babylon Editor** | 通用场景编辑器                                                                       | 场景树 / 属性面板 / 命令栈的组织方式（我们把"元素视图"做成场景树是同一个路子） |
| **viser**（nerfstudio）              | Python 侧 3D GUI + **WebSocket 消息协议**                                            | **实时交互的信道设计**：状态同步 vs 命令式消息的取舍                           |
| **model-viewer**（Google）           | web component 查看器                                                                 | 一点点即可：属性驱动的查看器配置（`<model-viewer>` 那种声明式接口）            |
| **Open3D WebRTC / Viser**            | 服务端渲染后推流                                                                     | **要避开的路线**：服务端渲染 + 推流会让我们失去客户端交互与离线能力            |

### 1.2 该抄的三样

1. **LOD 流式**（来自 Potree/Cesium）：现在 panel 是"一次性渲染子集，上限 6 万点"，
   真实点云 200 万点 → 必须改成"索引 + 按需取块"。**这是我们最大的短板**，也是 panel 阶段
   唯一无法用 mock 糊过去的地方（要么真做 LOD，要么明确接受小点云）。
2. **测量与标注的交互范式**（来自 Potree）：引导式取点、吸附到点、单位随尺度、标注可编辑。
   我们已有一套（引导 2/3/4 点 + 服务端算数值），重写时**照原样迁移**即可。
3. **编辑器 UX 细节**（来自 SuperSplat）：框选/裁剪的反馈、撤销栈的粒度、
   导出即发布（生成可分享链接）——后者对我们的"官网 + 分享"是顺手的能力。

### 1.3 不该抄

- **服务端渲染 + 推流**（Open3D WebRTC 类）：会牺牲交互延迟与离线能力，且 GPU 成本翻倍；
- **把场景编辑器当底座**（three.js editor 那种通用场景 JSON）：我们的数据模型是"点云 + 标注元素"，
  不是通用场景图；照抄会得到一堆用不上的抽象；
- **泼溅优先**（SuperSplat/GS 路线）：我们的产物是**测量级点云**，泼溅是另一条产品线，
  可以作为**未来的一种产物格式**接进来，但不要动核心数据模型。

### 1.4 前端技术选型（已定，见 ADR-0008）

Vite + TypeScript + Vue 3（`<script setup>` + Pinia）+ three.js（npm 依赖，**不再 CDN**）。
铁律：**`THREE.*` 对象不得进入 Vue 响应式系统**（`markRaw` / `shallowRef`），否则渲染循环会被 Proxy 拖死。

## 二、服务侧（阶段二）

### 2.1 参照对象

| 对象                                  | 是什么                                                            | 能从它身上拿到什么                                                                                                          |
| ------------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **NodeODM**                           | 处理节点 REST API（AGPL-3.0，航测开源界事实标准）                 | **作业形状**：`/info` 能力自述、`/options` 参数自述、`init→upload→commit` 预上传、队列状态码、`webhook`、`download/{asset}` |
| **WebODM**                            | 航测项目管理面板（Django，AGPL-3.0）                              | **控制面形状**：用户/项目/多节点聚合；但它**没有计量计费**                                                                  |
| **OGC API - Processes (18-062r2)**    | OGC 正式标准（含 OpenAPI 定义 + 合规测试）                        | **通用异步作业语义**：process → job 资源 → 状态/结果/删除；"标准"名头与合规套件                                             |
| **KServe Open Inference Protocol V2** | 推理服务事实标准（Triton/TorchServe/KServe 均实现）               | **worker 内部契约**（gRPC `ModelInfer` / REST 双协议）                                                                      |
| **Replicate `cog`**                   | 开源容器约定（`setup()/predict()` + `/predictions` + `/healthz`） | **worker 打包与生命周期的极简范式**（比 KServe 更轻）                                                                       |
| **Cesium ion / PDAL**                 | 瓦片与点云处理生态                                                | **产物侧**：3D Tiles 生成、COPC 转换（PDAL 一条命令）                                                                       |

### 2.2 该抄的三样

1. **`/info` 能力自述**：执行单元数、队列深度、输入上限 —— 把"这台机器能干什么"变成可查询事实；
2. **`/options` 参数自述**：处理参数的机器可读 schema（name/type/domain/default/help），
   客户端不再写死 `resolution` / `frame_count`；
3. **预上传 + webhook**：`init→upload→commit`（或 tus）替代一次性 multipart；完成回调替代纯轮询。

### 2.3 不该抄 / 必须换掉的

- NodeODM 的 **token 走 query 参数** → 换 `Authorization: Bearer`；
- NodeODM 的 **裸 `{error: string}` / `{success: bool}`** → 换 **RFC 9457 problem+json** + 稳定错误码；
- **单一 vendor 血统**：NodeODM 只有 ODM 一系实现，"事实标准"要打折看 —— 作业语义仍以
  **OGC API-Processes** 为准，只借 NodeODM 的**词汇与端点形状**（详见 ADR-0006）。

### 2.4 许可红线

| 项目                                   | 许可                                    | 我们能做什么                                                           |
| -------------------------------------- | --------------------------------------- | ---------------------------------------------------------------------- |
| NodeODM / WebODM                       | **AGPL-3.0**                            | **照协议形状实现**可以（接口形状不受版权保护）；**拷代码会传染**，禁止 |
| Potree / SuperSplat / three.js         | 宽松（MIT/BSD 类，以仓库 LICENSE 为准） | 前端库层面可直接依赖                                                   |
| OGC / KServe / RFC / CloudEvents / tus | 规范（无版权障碍）                      | 直接按规范实现                                                         |

---

## 三、结论（一句话）

**panel 侧照着"编辑器三件套"（LOD 流式 + 测量交互 + 撤销/发布）做；
服务侧照着"作业协议两件套"（OGC API-Processes 语义 + NodeODM 形状）做；
唯一必须自研的是控制面与计量计费 —— 开源界没有。**
