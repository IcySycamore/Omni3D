# ADR-0005：热路径与配额 —— 后付费 + 护栏 + 扣押产物

- 状态：Accepted
- 日期：2026-09-17
- 关联：ADR-0004、[`../02-wire-protocol.md`](../02-wire-protocol.md) §6

## 背景

一次重建的**实际用量**（点数/体素/三角面）只有跑完才知道，而额度校验发生在**提交时**——
两者之间隔着一次 GPU 前向。参考实现的做法是"提交前查额度（`can_start`）+ 完成后记账"，
并保留了一套 `Authorize`/reservation 式的设计草案。

## 决策

**提交时不查配额**（可用性优先），只查**认证**；完成后按实际用量扣费（`Charge`），
并配一套"不叫配额"的护栏：

1. **认证必须同步**（Key 有效 + 未吊销）——否则"吊销"形同虚设；
2. **限流**：per-key / per-IP 速率 + **并发任务上限** + **全局队列深度上限**（满了 429，不入队）；
3. **输入上限**：帧数 / 分辨率 / 上传字节 / 总像素预算（`/v1/info` 声明，客户端据此拦提交）；
4. **欠费 `arrears`**：`Charge` 说额度不足 → 账号置 `arrears` + **扣押产物**（结清才签发产物 URL）
   → 已欠费账号下次提交直接 403（这是**状态位判断**，不是额度计算）；
5. **扣减顺序不变**：计划包 → 同计量用量包 → 余额；每步写流水（`ledger`）；
6. **幂等**：`Idempotency-Key` 防重复建任务；用量以 `task_id` 幂等上报。

## 代价与后果

- **公司替客户承担"跑完才发现付不起"的风险**：算力已经花掉，产物是唯一能握住的东西 →
  所以**扣押产物不是可选项**，去掉它就等于把欠费变成确定损失；
- **不做预扣**：恶意/失控客户端可以持续排队（靠 429/并发上限兜底，而不是靠钱包）；
- **多了一个状态位**（`arrears`）与一套结清流程（补缴 → 释放产物：**尚未设计**）；
- **验证阶段（BETA_FREE）行为要写死**：额度免费发放、**包照扣、余额不扣、额度不足不拦**。

## 未决

1. `arrears` 的结清流程：补缴后自动释放产物？保留多久？欠费是否影响历史数据访问？
2. 限流与并发上限的**具体阈值**（按 GPU 槽位与带宽定，需压测）；
3. 是否需要"余额不足提前预警"（在提交时只做**提示**不做拦截）。
